# プロンプトバトル 設計書（骨組み）

## 概要

骨組みのゴールは、「プレイヤー1人＋CPU5人の6人戦」が1台のPCだけで最初から最後まで通して遊べること。パーツ選び→組み立てとプロンプト→エージェントが操縦するバトル→ダメージ→配布とパーク→次のラウンド、を最後の1人が決まるまで回す。見た目は箱や円柱の仮のものでよい。

**骨組みに含めるもの**

- 6人のラウンド制サバイバル（体力100、脱落、順位）
- フレーム・武器・スキルの3種類のパーツと、出るたびに変わるステータス
- 開始時のパーツ選び、ラウンド後の配布とパーク
- 操縦エージェントが2秒おきに方針を決め、ゲームがその方針で機体を動かす仕組み
- 自分の試合の観戦（ほかの2試合は画面に出さず裏で計算する）

**骨組みに含めないもの**：通信対戦、外部観戦、本番の3Dモデルと画面効果、本番のLLM（最初はルールで動く仮の頭脳で代用する）

**設計の方針**

1. **試合の計算と画面を分ける。** 試合の計算は画面を一切知らない純粋なコードにし、画面は計算結果を読んで描くだけにする。後で計算部分だけを画面なしのサーバーに移せば、通信対戦になる。
2. **操縦エージェントは差し替えできる部品にする。** 「戦況を受け取って方針を返す」という入出力だけを決め、中身は仮の頭脳→本番のLLMと入れ替える。
3. **数値はコードに書かず、データファイルに分ける。** パーツの性能やダメージの式は未決定が多いので、調整しやすくしておく。
4. **同じ種からは同じ結果になるようにする。** 乱数は試合ごとの種から作り、バグの再現と自動テストをしやすくする。

## 全体構成

4つの層に分ける。

```text
┌──────────── 画面（view/）─────────────┐
│ Godotのシーン。状態を読んで描くだけ        │
└──────┬─────────────────▲───────────┘
       │ 操作                │ 状態とイベント
       ▼                    │
┌ ─ ─ ─ ─ 試合の計算（core/）─ ─ ─ ─ ─ ┐  ← 点線の範囲は、そのまま
│ MatchSession / BattleSim など        │     画面なしのサーバーへ移せる
└ ─ ─┬─────────────────▲─ ─ ─ ─ ─ ─ ┘
     │ 観測（戦況）          │ 方針（インテント）
     ▼                    │
┌──── 操縦エージェント（agent/）────────┐
│ AgentBrain の下で MockBrain / LlmBrain │
│ / ReplayBrain を差し替える             │
└────────────────────────────────┘

データ（data/）：parts.json / perks.json / rules.json を core が読む
```

画面と試合の計算は「操作」と「状態とイベント」だけでつながり、エージェントは観測を受けて方針を返すだけにする。

## 画面と状態の流れ

```text
タイトル
  → 開始時のパーツ選び（全員同じ候補から種類ごとに1つ）
  → [ラウンド開始]
     組み立てとプロンプト入力（45秒）
  → バトル（自分の試合を観戦。ほかの2試合は裏で計算）
  → ラウンド結果（ダメージ、脱落）
  → 生き残りが1人？ ─はい→ 最終順位
       │いいえ
       ▼
     自分は生きている？ ─いいえ→ 観戦だけ続けて次のバトルへ
       │はい
       ▼
     パーツ配布（5つ）とパーク選択 → [次のラウンド開始] へ戻る
```

1つの段階が、試合（MatchSession）の1つの段階にあたる。画面は今の段階を読んで対応する画面を出すだけ。プレイヤーが先に脱落した場合は、組み立てとパーク選択を飛ばして観戦だけを続け、最終順位まで進む。

## データの形

データは「型（どんなパーツがあるか）」と「実物（配られた1個1個）」を分ける。同じパーツでも出るたびにステータスが変わるので、実物は「どの型か」と「その回のステータス」を持つ。

| データ | 持つ情報 | 備考 |
| --- | --- | --- |
| パーツの型（PartDef） | ID、名前、種類（フレーム／武器／スキル）、各ステータスの最小値と最大値、固定値、動き方（behavior）、見た目（モデルの場所） | データファイルに書く。フレームは武器とスキルの枚数も持つ |
| パーツの実物（PartInstance） | 固有ID、型のID、その回のステータス | 配られるときに範囲内で抽選する |
| ステータスの中身 | フレーム：HP、移動速度の低下。武器：ダメージ、ノックバック。スキル：スキルごとの性能値 | `docs/game-rules.md` の「パーツ」の節のとおり。出るたびに振れるのはこれだけ |
| 固定値（fixed） | フレーム：重さ、曲がりやすさ。武器：次に使えるまでの時間、当たる角度の幅、届く距離、射程、弾数など。スキル：再使用までの時間、効果時間、届く距離、使える回数 | 抽選しない値。型ごとに `data/parts.json` に書く |
| 動き方（behavior） | 武器：grind（触れている間削る）、strike（叩く）、lift（ひっくり返す）、ram（体当たり）、shoot（弾を撃つ）、hook（釣り針を撃って自分の前まで引き寄せ、少し動けなくする）、flame（炎を浴びせ続け、ときどき火傷〈続けてダメージの状態異常〉にする）。スキル：booster、shield、repair、shockwave、emp、overclock、self_destruct（使わなくても動く。HPが0になると速くなって突っ込み、一定時間後に自爆。自爆で相手を壊せば引き分け） | バトルでの動き方を決める。同じ動き方で数値違いのパーツを増やせる |
| 機体（Build） | フレーム1つ、武器のリスト、スキルのリスト | 武器とスキルの数はフレームの枚数まで。同じパーツを2回は使えない |
| パーク（PerkDef） | ID、名前、効果（例：HP+5%） | データファイルに書く |
| プレイヤー（Player） | ID、名前、人間かCPUか、体力（初期100）、手持ちパーツ、取ったパーク、今の機体、今のプロンプト、生存か、順位 | CPUも同じ形。違うのはプロンプトと組み立てを自動で決めることだけ |
| 試合（MatchSession） | 6人のプレイヤー、今のラウンド番号、今の段階、過去の対戦履歴、乱数の種 | ゲーム全体の状態はここに集める |
| ラウンド（Round） | ペアの一覧、各バトルの結果、各人へのダメージ | 終わったら履歴に残す |
| バトルの状態（BattleState） | 経過時間、機体2体の位置・向き・速度・HP・状態、弾、今の方針 | 1刻みごとに更新。画面はこれを読んで描く。`core/battle_sim.gd` が全体を、`core/battle_robot.gd` が機体1体分を持つ |
| バトルの結果（BattleResult） | 勝った人、決着のつき方（破壊／穴／時間切れ）、残りHPの割合、与えたダメージ | ダメージ計算の「差」に使う |

画面に届ける瞬間的な出来事（命中、穴に落ちた、方針を変えたなど）は、状態とは別に「イベント」として流す。実況や火花の演出はイベントを見て出す。

## バトルの仕組み

バトルは毎秒60回の固定刻みで計算し、画面の描画速度とは切り離す。操縦は2段構えで、エージェントが「方針（インテント）」を決め、ゲーム側の「実行役」がその方針を毎刻みのハンドルとアクセルに直す。

**物理は自前の平面の計算にする。** Godot内蔵の物理は使わず、上から見た平面で、位置・速度・円どうしの衝突・押し合い・吹き飛ばしを自分で計算する。ノードを使わず画面なしで動き、同じ種なら必ず同じ結果になり、数百試合を一瞬で回せるため。3Dの画面はこの計算結果を読んで描く。ひっくり返る・穴に落ちるといった高さのある動きは演出として見せる。機体が本当に宙を舞ったり転がったりする物理が必要になったら、計算に高さを足す形で見直す。

**武器はすべて機体の前に付く扱いにする。** 近接の武器は「前方の決まった角度の幅」と「接触から届く距離」に相手が入ったときに当たり、撃つ武器は前方の狭い角度に相手がいるときに撃つ。後ろから受けた攻撃はダメージが増える。

**1刻みでやること（この順番）**

1. 考える時刻かどうかを確かめる。前回から2秒たったか、考え直す切っ掛けになる出来事が起きていれば、各機体のエージェントに戦況を渡す
2. エージェントの答えが届いていれば、その機体の方針を入れ替える。届いていなければ前の方針を続ける
3. 実行役が、今の方針から目標地点と向きを決め、ハンドル・アクセル・武器・スキルの使い方を出す
4. 物理を進める（移動、衝突、押し合い、吹き飛ばし）
5. 武器とスキルの当たり判定とダメージを処理する
6. 穴、回復パック（取る・別の場所に出直す）、場外を処理する
7. 決着したかを判定し、この刻みで起きた出来事をイベントとして流す

**考え直す切っ掛けになる出来事**：大きく被弾した、ひっくり返された、弾が切れた、相手が穴の近くに来た、HPが半分を切った。ただし連続して呼ばないよう、前回から最低0.5秒は空ける。

**決着のつき方**

- 相手のHPが0になる（破壊）
- 相手が穴に落ちる
- 制限時間（仮に75秒）が終わる。残りHPの割合が高い方の勝ち。ほぼ同じ（差が1%未満）なら引き分け

自分の試合は画面に出して実時間で進める。ほかの2試合は同じ計算を画面なしで回す。仮の頭脳なら一瞬で終わるが、本番のLLMでは実時間でしか考えられないので、最初から「3試合とも実時間で並んで進む」前提で作る。

## 操縦エージェントの入出力

エージェントは「戦況（観測）を受け取り、方針を返す」だけの部品にする。中身を仮の頭脳から本番のLLMに入れ替えても、バトル側は何も変えない。

**共通の入口（AgentBrain）**

- `begin(prompt, build, rules)`：ラウンドの始めに1回だけ呼ぶ。プレイヤーのプロンプト、機体の説明（パーツの名前・動き方・ステータス）、ルールなど、試合中に変わらないものを渡す
- `request(observation)`：考えるたびに呼ぶ。すぐに戻り、答えは後から届く（非同期）
- `poll(now)`：答えが届いていれば方針を返し、まだなら空を返す。`now` は今の試合時間（秒）

答えを待たずに試合を進めるのが大事。遅いPCで答えが間に合わなくても、機体は前の方針で動き続ける。

`poll` に試合時間を渡すのは、仮の頭脳の遅れを試合時間で数えるため。こうすると、仮の頭脳を使う試合は同じ種なら必ず同じ結果になり、テストで数百試合を一瞬で回せる。本番のLLMは `now` を使わず、実際の時間で答えが届いたら返せばよい（その場合、同じ種でも結果は毎回少し変わる）。

**渡す戦況の例**（毎回はこの程度の小ささに収める）

```json
{"t": 31.5, "time_left": 43.5,
 "me": {"hp": 62, "pos": [-4, 3], "facing": 90, "ammo": 12, "stunned": false, "near_pit": false,
        "intent": "charge", "skills": [{"name": "ブースター", "behavior": "booster", "ready": true}]},
 "enemy": {"hp": 80, "dist": 6.2, "dir": "前方やや右", "near_pit": true, "behind_me": false,
           "facing_me": true, "stunned": false},
 "repair": {"dist": 9.0, "left": 30}, "events": ["被弾:ハンマー:18"]}
```

- `hp` は最大HPに対する割合（%）。`ammo` は撃つ武器の残り弾の合計で、撃つ武器がなければ `null`
- `dir` は自分の向きから見た相手の方向（前方／前方やや右／右／後方やや右／後方 など）
- `behind_me` は相手が自分の後ろ側にいるか、`facing_me` は相手がこちらを向いているか
- `events` は前回考えてから自分に起きたこと（最大5件）

**返す方針の例**

```json
{"intent": "push_to_pit", "skill": null, "say": "穴に寄せるっす！"}
```

**方針の種類（仮）**

| 方針 | 実行役がやること |
| --- | --- |
| charge | 相手にまっすぐ突っ込む |
| flank | 相手の後ろに回り込んでから攻める |
| keep_distance | 相手を向いたまま距離を保つ（射撃向き） |
| retreat | 相手から逃げる |
| push_to_pit | 相手をはさんで穴の反対側に回り、穴へ押す |
| go_repair | 一番近い回復パックを取りに行く（場になければ相手から離れる） |
| circle | 相手の周りを回る |
| hold | その場で相手を向いて待つ |

`skill` はその場で使うスキルの番号、`say` は操縦士の一言（実況や吹き出しに使う）。種類はバトルを作りながら増減させる。

**頭脳の種類**

| 頭脳 | 中身 | 使う場面 |
| --- | --- | --- |
| 仮の頭脳（MockBrain） | プロンプトのキーワード（「突撃」「穴」「撃」「修理」「回り込」など）で作風を決め、戦況から決まった規則で方針とスキルを選ぶ。わざと試合時間で0.3〜1.5秒遅らせて答え、本番の遅さを真似る | 骨組みの開発中。CPUプレイヤー |
| 本番の頭脳（LlmBrain） | llama.cppで小さいLLMを動かす。変わらない部分は最初に読ませておき、出力は方針の形に強制する（詳しくは「本番の頭脳」の節） | 人間の機体と、1人用ではそれと戦う相手（CPUか記録の再生）。ほかの試合は仮の頭脳のまま |
| 記録の再生（ReplayBrain） | 保存しておいた他人の機体とプロンプトで動かす | 生き残りが奇数のときの相手（後で足す） |

本番の頭脳が壊れた答えを返したときは、前の方針を続け、操縦士に「えっと…」と言わせる。失敗もポンコツらしさとして見せる。

## 本番の頭脳

**つなぎ方**：llama.cpp 公式の `llama-server.exe` をゲームが裏で起動し、PC内の通信（127.0.0.1）で問い合わせる。Godot への組み込み部品を自前でビルドせずに済み、出力の形の強制や、変わらない前半部分の使い回しを公式の機能で使える。サーバーはゲームの起動時に1回だけ立ち上げて試合をまたいで使い回し、ゲームを閉じるときに止める。問い合わせは待たずに少しずつ進め（`agent/http_job.gd`）、答えが届くまで機体は前の方針で動き続ける。

**誰の機体を動かすか**：通信対戦で各PCが動かすのは自分の機体のエージェントだけ（企画メモ「懸念点と対策」）。1人用では、自分の機体に加えて、自分と戦っている相手（CPUか記録の再生）も本番の頭脳で動かす（`data/llm.json` の `cpu_opponent`。相手もプロンプトどおりに考えて動くほうが、試合として見応えがあるため）。ほかの試合のCPUは仮の頭脳のまま。サーバーは2つの頭脳に同時に答えられるよう `parallel`（llama-server の `-np`）を 2 にし、それぞれの変わらない前半部分を別々に使い回す。

**2つの頭脳を同時に動かしたときの速さ**（Ryzen 7 7735U・CPUだけ・Qwen3.5-2B。2秒おきに2つの頭脳から同時に問い合わせ、16秒間）：1つあたり約4.5〜7秒で答え、それぞれ16秒で3〜4回しか方針を決められない。最初の1〜2回は前半部分の計算が重なって8秒の上限を超えることが多い。1つだけのとき（約2.7秒）より明らかに遅く、相手まで本番の頭脳にすると判断の間隔がおよそ倍になる。

**問い合わせの中身**
- 変わらない部分（役目、方針の一覧、スキル、機体、答えの形、プレイヤーのプロンプト）は試合の始めに1回だけ組み立てる。毎回はその後ろに戦況だけを足す
- 戦況は、位置や向きの数字を省いた小さな JSON で渡す（短い日本語の文で渡す方法も試したが、正答率が下がった）
- 出力は文法（GBNF）で `{"intent":"…","skill":番号かnull,"say":"…"}` に縛る。方針は8種類、スキルは持っている番号か null、一言は12文字まで
- 小さいモデルの考える過程（thinking）は使わない
- 答えを待つ上限は8秒（実時間）。超えたら失敗として「えっと…」にする
- 問い合わせ中に次の戦況が来たら、終わってから一番新しい戦況だけを送る

**サーバーが使えないとき**：サーバーやモデルが見つからない、起動できないときは、本番の頭脳の中に持っている仮の頭脳で動く。画面に「操縦士：仮の頭脳（理由）」と出す。

**モデルの置き場所**：`tools/fetch_llm.ps1` で、版を固定した公式の配布物を取ってきて SHA256 で照合する。置き場所は既定で「ユーザーフォルダ\Godot\llm」（プロジェクトの中に置くと、OneDrive などの同期で数GBが送られるため）。Git には入れない。

**測った結果**（Ryzen 7 7735U・CPUだけ。`tools/llm_bench.gd` の12通りの指示と戦況を2回ずつ）

| モデル | 指示どおり | 指示が変わった直後 | 2回目以降 | ゲームの中の答えの間隔 |
| --- | --- | --- | --- | --- |
| Qwen3.5-0.8B（Q4_K_M） | 38% | 2.4秒 | 1.3秒 | 約1.8秒 |
| LFM2.5-1.2B-JP（Q4_K_M） | 50% | 4.2秒 | 4.1秒 | 約5.4秒 |
| Qwen3.5-2B（Q4_K_M） | 63% | 4.9秒 | 2.7秒 | 約3.5秒 |

- LFM2.5 はこの使い方では前半部分の使い回しが効かず、毎回すべてを計算し直すため遅い
- ゲームの中では3Dの描画と試合の計算がCPUを取り合うので、測定ツールより遅くなる
- どのモデルも「HPが減ったら」「体力が3割を切ったら」のような数値の条件の判断が苦手。伸ばすには追加学習が本筋
- 骨組みの初期値は Qwen3.5-2B（`data/llm.json` の `model` で替えられる）

## 通信対戦

最初の目標は「IPアドレスを入れてつなぐ」まで。公開用のサーバーの置き場所やマッチングは次の段階に回す。

**作り**
- **サーバー**（`net/game_server.gd`、起動は `net/server_main.tscn`）：画面なしの Godot で動き、試合（MatchSession）をそのまま計算する。試合の結果はサーバーだけが決める。AIは動かさない
- **クライアント**（`net/game_client.gd`）：サーバーから届く状態を、試合の写し（`net/remote_session.gd`・`net/remote_sim.gd`）に当てはめる。写しは MatchSession・BattleSim と同じ名前で読めるので、画面はそのまま使える。操作はサーバーへ送るだけで、締め切りや進行はサーバーが決める（スクラップの4つの操作も同じ。再抽選の結果は、次に届く状態で分かる）
- **頭脳**：サーバーには「遠隔の頭脳」（`net/remote_brain.gd`）を置き、共通の入口（begin / request / poll）の形のまま、問い合わせをそのプレイヤーのPCへ転送する。考えるのは各PCの頭脳（本番のLLMか仮の頭脳）。答えの中身はバトル側が確かめる
- **層**：通信はノードを使うので `net/` に分ける。`core/` と `agent/` は画面なしのまま

**流れ**：待合室（最初に入った人が開始できる）→ 試合 → 最終順位 → 待合室。足りない人数はCPUで埋める（2〜6人）。パーツ選び・組み立て・パーク選びは、つながっている人間が全員操作し終えたら締め切りを待たずに進む。ラウンド結果は数秒見せてから進む。時間は `data/rules.json` の `online`

**見せてよいもの**：状態は見る人ごとに組み立てる。生き残っている間は、自分以外のプロンプトとほかの人の手持ちを送らない（企画メモ「観戦」）

**接続が切れたら**：その人の機体とプロンプトのまま、サーバーの仮の頭脳が操縦を引き継ぎ、組み立てとパーク選びもCPUと同じ方法で決める。同じ名前で入り直せば操作を取り戻せる。人間が全員いなくなったら試合を終えて待合室に戻る

**通信の中身**（`net/protocol.gd`）：Godot の ENet で、辞書を `var_to_bytes` にして送る（物は戻さないので、相手が何を送ってきても安全）。試合の状態は変わったときだけ（最大で毎秒5回）、バトルの動きは毎秒20回。クライアントは届いた位置へ滑らかにつなぐ。どれも確実に届く送り方を使う（バトルの動きが1回で数KBになり、届く保証のない送り方の上限を超えるため）

**ホストする**：画面の「ホストする」で、このPCに画面なしのサーバーを裏で起動して自分もつなぐ。抜けるときにサーバーも止める

## 見た目

目標は企画メモの「薄暗く汚れた質感」。見た目の値はすべて `view/look.gd` に集め、雰囲気の調整はそこだけ触る（ゲームの計算には関わらない値なので `data/` には置かない）。

- **低い解像度で描いて拡大**：3Dのアリーナを画面の1/3の解像度（427x240）で描き、ぼかさずに拡大する
- **画面効果**（`view/shaders/post_grime.gdshader`）：ざらつき、ディザしながら色の段数を減らす、周辺を暗くする、色味。アリーナには強く、メニューを含む画面全体には薄くかける。文字の板は効果の上に出して読みやすさを保つ
- **照明**：真上に吊った電球（影を落とす）、斜めからの弱い冷たい光、穴の縁を照らす赤い光、回復パックの水色の光、壁の外の松明8本（`view/arena/torch.gd`。影なしで、揺れは時間の関数）、霧
- **質感**（`view/grime.gd`）：画像ファイルを使わず、ノイズの模様で色むらやこすれを出す仮の質感。本番の3Dモデルとテクスチャに置き換える前提
- **演出**：被弾で火花が散る。強い被弾・ひっくり返し・穴落ちで画面が揺れる（揺れは時間の関数で作り、乱数は使わない）
- **撃つ武器の弾**（`view/arena/shot_fx.gd`）：機関銃は細長く光る曳光弾、ロケットは弾体・噴射炎・煙の尾。撃った瞬間に銃口が光り、機体や壁に当たった所で火花が散る（撃ってきた方へ跳ね返す）。ロケットは当たると爆発する。弾には試合の中で弾ごとに違う番号と撃った武器のパーツIDを持たせ、画面はそれで弾を見分ける（計算には使わない）。倍速などで弾が一度も映らずに当たったときは、被弾の記録から火花を出す
- **機体の頭上の文字**：低い解像度では読めないので、3Dの位置に合わせて2Dで重ねる
- 描画方式は Compatibility のまま。画面効果も Compatibility で動く範囲で作っている
- Compatibility では1つの物を照らせる光は8つまで。床は5メートル四方のタイルに分け、どの物にも近くの光だけが当たるようにしている（`tests/test_arena_view.gd` で8つ以下を確かめる）。光を足すときはこの数に気をつける

## ラウンドの進行

ラウンドの進行はすべて「試合（MatchSession）」が受け持つ。画面は「今はどの段階か」を読んで対応する画面を出し、プレイヤーの操作（パーツを選んだ、プロンプトを確定したなど）を試合に伝えるだけにする。

**開始時のパーツ選び**：フレーム・武器・スキルをそれぞれ5つずつ抽選し、全員に同じものを見せる。各自が種類ごとに1つずつ選ぶ。骨組みでは同じパーツを複数人が選べる形にしておき、取り合いにするかは後で決める。

**ペア作り**

1. 生き残っている人を並べ替え、直前に当たった相手と組まない組み合わせを乱数で探す
2. そういう組み合わせがなければ、条件を外して組む
3. 生き残りが奇数のときは、余った1人を、脱落した人の最後の機体とプロンプト（記録の再生）と戦わせる。この試合は勝っても負けても、記録側はダメージを受けない

**ダメージ計算**

負けた人のダメージは、`docs/game-rules.md` のとおり「順位による分」と「差による分」の合計にする。具体的な値は未決定なので、仮の式で作ってデータファイルから変えられるようにする。

```text
damage = A × rank + B × margin
```

- rank：負けた人の、残り体力での今の順位（1が最上位）。上位ほど重くするか軽くするかは後で決める
- margin：勝った側の機体の残りHPの割合（0〜1）。大差で負けるほど大きい
- A、Bの仮の値は「仮置きした値」の節を参照

**ラウンド後の配布とパーク**

- 各プレイヤーにパーツを5つ配る。フレーム・武器・スキルを各1つ以上含め、中身は人ごとに変える
- パークを選ばせる（骨組みでは3つの候補から1つ）。パークの効果はその試合の間ずっと積み重なる
- 脱落した人には配らない

**スクラップ**（`MatchSession` の `scrap_part` / `reroll_part` / `resolve_reroll` / `reroll_perk_choices`）

- 使えるのは `scrap.unlock_round` ラウンド目から。負けたラウンドの分（`scrap.loss_bonus`）だけは最初から貯まる（引き分けはもらえない）
- 解体：組み立てとパーク選びの段階で、機体（`Player.build`）に付けていない手持ちのパーツを解体し、種類ごとの量をもらう。抽選の良さ（`Loot.roll_quality`）が上半分なら上乗せ
- 再抽選：組み立ての段階で、手持ちのパーツの性能を範囲内で引き直す。結果は `Player.pending_reroll` に保留し、`resolve_reroll` で「元のまま／新しい性能」を選ぶまで次の再抽選はできない。選ばないまま組み立てを締め切ったら元のまま。画面は使っているパーツにだけボタンを出す
- パーク候補の引き直し：パーク選びの段階で、選ぶ前に1ラウンド `scrap.reroll_perks_per_round` 回まで
- 乱数は試合の種から名前つきで分ける（`round/N/reroll/人/回数` など）。同じ種・同じ操作なら同じ結果になる
- CPU は組み立ての締め切りのときに使う（`agent/cpu_planner.gd` の `plan_upkeep` / `accept_reroll`）

**脱落と順位**：体力が0になった人から脱落し、脱落した順に下の順位が決まる。同じラウンドで複数人が脱落したら、残り体力がよりマイナスになった人を下にする。生き残りが1人になったら試合終了。プレイヤーが先に脱落しても、残りのCPU同士の試合を観戦しながら最後まで進める。

## フォルダ構成

「試合の計算（core）」「エージェント（agent）」「画面（view）」をフォルダで分ける。coreとagentはシーンやノードに依存しない純粋なスクリプトにし、viewだけがGodotのシーンを持つ。

```text
prompt-battle/
├─ project.godot
├─ data/                  数値と定義（ここだけ触ればバランス調整できる）
│  ├─ parts.json          パーツの型とステータスの範囲
│  ├─ perks.json          パークの定義
│  └─ rules.json          体力、制限時間、ダメージの係数など
├─ core/                  試合の計算（画面を知らない）
│  ├─ game_data.gd        data/ の3ファイルの読み込みと検査
│  ├─ part_instance.gd    パーツの実物
│  ├─ build.gd            機体と組み立ての検査
│  ├─ match_session.gd    試合全体の状態と段階の進行
│  ├─ pairing.gd          ペア作り
│  ├─ damage.gd           ダメージ計算
│  ├─ loot.gd             パーツの抽選、配布、パーク候補
│  ├─ battle_sim.gd       バトル1試合の計算（固定刻み）
│  ├─ battle_robot.gd     バトル中の機体1体の状態
│  ├─ robot_driver.gd     方針をハンドルとアクセルに直す実行役
│  ├─ observation.gd      エージェントに渡す戦況を作る
│  └─ rng.gd              種から作る乱数
├─ agent/                 操縦エージェント
│  ├─ agent_brain.gd      共通の入口
│  ├─ mock_brain.gd       仮の頭脳
│  ├─ llm_brain.gd        本番の頭脳（llama-server に問い合わせる）
│  ├─ llm_server.gd       llama-server を裏で起動・確認・停止する
│  ├─ llm_config.gd       本番の頭脳の設定（data/llm.json）を読み、サーバーとモデルを探す

│  ├─ default_agents.gd   試合に渡す頭脳とCPUの判断のセット

│  ├─ game_server.gd      サーバー：待合室、試合の進行、状態の送信、切断の引き継ぎ
│  ├─ server_main.tscn    画面なしのサーバーの入口
│  ├─ game_client.gd      クライアント：つなぐ、状態を受け取る、自分の頭脳を動かす
│  ├─ remote_session.gd   試合の写し（MatchSession と同じ名前で読める）
│  ├─ remote_sim.gd       バトルの写し（BattleSim と同じ名前で読める）
│  ├─ remote_brain.gd     サーバーに置く遠隔の頭脳
│  ├─ net_agents.gd       サーバーが使う頭脳とCPUの判断のセット
│  └─ protocol.gd         やり取りの形と、見る人ごとの状態の組み立て
├─ view/                  画面（Godotのシーン）
│  ├─ main.tscn           段階に合わせて画面を切り替える

│  ├─ ui_text.gd          画面で使う文字の組み立て（パーツの説明、実況の行など）
│  ├─ title/              タイトル
│  ├─ draft/              開始時のパーツ選び、配布、パーク選び

│  ├─ arena/              3Dのアリーナ、機体の表示、実況

│  ├─ online/             通信対戦の入口と待合室
│  └─ debug/              開発用の画面（上から見た2Dの観戦画面など。製品には出さない）

```

`tests/` では、画面なしのGodotでCPU6人の試合を何百回も回し、「必ず決着する」「同じ種なら同じ結果になる」「数値が壊れない」を確かめる。Claude Codeが自分で動作を確かめられるようにするための仕組み。

## 実装の順番

画面より先に試合の計算を作り、自動テストで「CPU6人の試合が最後まで回る」ことを確かめてから、画面をかぶせる。各段階の完成の目安を満たしたら次に進む。

1. **データと乱数**：`data/` の3ファイルと読み込み、種から作る乱数。完成の目安：同じ種で同じパーツが同じステータスで出る
2. **バトル1試合（画面なし）**：固定刻みの計算、実行役、決着判定。頭脳は仮の頭脳。完成の目安：ランダムな機体同士で数百試合回して、必ず決着し、勝ち方が偏りすぎない。「偏りすぎない」の基準は、①破壊・穴落ち・時間切れのどれも5%以上80%以下、②先に置かれた側の勝率が40〜60%、③引き分けが20%未満、④どのフレーム・武器も勝率25〜75%。試合を目で確かめるため、開発用の2Dの観戦画面（`view/debug/`）もここで作る
3. **ラウンドの進行（画面なし）**：ペア作り、ダメージ、配布、パーク、脱落。完成の目安：CPU6人の試合が最後の1人まで進み、何ラウンドかかるかが測れる
4. **画面の骨組み**：タイトル、パーツ選び、組み立てとプロンプト、結果。完成の目安：プレイヤーが操作して段階が進む（バトルはまだ文字だけでよい）
5. **アリーナの3D表示**：箱の機体、穴、修理ステーション、実況の文字。完成の目安：自分の試合を観戦でき、操縦士の今の方針と一言が見える
6. **通しで遊ぶ**：タイトルから最終順位まで。完成の目安：メンバーが説明なしで1試合遊べる

ここまでで骨組みは完成。次は「本番の頭脳への差し替え」「見た目（照明と画面効果）」「通信対戦」を、それぞれ独立して進められる。
